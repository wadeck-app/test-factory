# Test factory: operating guide

Tasks (local `task` storage today) go through triage, plan, build, integration, CI and deployment with no human step until the promotion of `integration` to `main`. Design decisions and open items: `.claude/plans/2026-11-14_factory-architecture.md`.

## Task lifecycle

| Status | Set by | Meaning |
|---|---|---|
| `new` | creator | not analysed |
| `backlog` | triage | type and priority set |
| `planned` | plan | acceptance criteria written, waiting for a builder (`READY: no` puts it `on-hold` with the question) |
| `in-progress` | dispatcher | a builder works on branch `<taskId>-<slug>` |
| `integrating` | build handler | branch pushed, waiting for the integrator |
| `integrated` | integrate flow | merged into `integration`; terminal for `task`, so it releases `blockedBy` links |
| `done` | you | promoted to `main` by hand |
| `on-hold` | you, or a failed run | never picked; running work for it is cancelled |

`question` and `audit` tasks are parked `on-hold` by the triage: nothing to implement.

## Pieces

| File | Role |
|---|---|
| `flows/00_pm.yml`, `lib/pm.mjs` | `npm run pm -- "<goal>"`: read-only PM splits a goal into dependent tasks |
| `flows/01_triage.yml`, `02_plan.yml` | read-only analysts on the reader clone `_test-factory_ro1` (synced on `origin/integration` before each run) |
| `flows/03_build_<type>.yml` | GENERATED by `lib/generate-build-flows.mjs` (`npm run generate:flows`; CI fails when stale). Host sync and install, model step with no git, gates in the VM, host commit and push |
| `flows/04_integrate.yml` | merge without conflict, gates, push `integration`, wait for its CI, package, deploy, smoke test |
| `flows/05_deploy.yml` | manual redeploy of a commit: `flow run flows/05_deploy.yml -i sha=<commit> --wait` |
| `lib/dispatch.mjs` | deterministic dispatcher: claims with `task next`, starts flows; roles in order integrate, build, plan, triage |
| `lib/on-flow-event.mjs`, `on-hold.mjs` | queue handlers: apply the result of a run, cancel runs of a held task |
| `subscribers.reference.yml` | the queue subscribers that wire events to the handlers (installed with `queue sub add`) |

## Rules the flows enforce

- The model never runs git; commit, push and merge are host scripts.
- Dependencies are installed on the host (`install-deps.sh`, Linux binaries, no install scripts); no registry token reaches the VM. A change to a `package.json` or the lockfile is refused by the gates.
- Gates: build, tests, violations, `app-core-cli check`; a bug fix must add or change a test file.
- Deployment happens only after the CI of the pushed `integration` commit passes, goes to the app-core of the HOST (port from its config), then a read-only smoke test calls every data source of the views. Copies: `.flow/deploy/<id>/<version>` (3 kept), current one in `.flow/deploy/<id>.current.json`.
- An event of a run is ignored when the task is no longer in the status that flow works on.

## Dispatcher settings (environment)

| Variable | Default | Meaning |
|---|---|---|
| `FACTORY_BUILDERS` | 1 | builds at once |
| `FACTORY_ANALYSTS` | 3 | triage and plan at once (3 reader clones `_ro1..3`, `READER_CLONES` in `flows/lib/factory.mjs`) |
| `FACTORY_SANDBOXES` | 3 | runs of all roles together (max workers of the sandbox source) |
| `FACTORY_PROJECT` | `test-factory` | task and flow project |

A dispatcher that finds the lock taken waits for it (3 minutes at most).

Parallel analysts are configured but NOT yet parallel. Measured 2026-11-15 (flow 1089, source `sandbox-builder-1` with `--max-workers 3`): with the sandbox plugin built before the `run-hold` change, 2 of 3 concurrent runs failed with "This worker already serves run"; with the rebuilt plugin (`wrapper.cjs` from `agent-fleet/packages/flow-sandbox`, copy it over the `--plugins-dir` copy and restart the daemon) nothing fails, but the daemon starts only ONE worker and the runs wait for it (15, 23, 30 s for a 15 s triage). flow-owner is fixing the scale-up (the daemon does not ask the source for another worker when one already meets `requires:`); retest with `flow worker list` during 3 concurrent runs. A run refused by a busy worker is sent back by the handler (comment, claim released). Load seen with one worker: CPU 26% at most, RAM 55 to 61%; the load of 3 simultaneous sandboxes is not measured yet. Reverse: see decision D10.

## Daily use

- Create a task: `task new "<title>" --description-file - -p test-factory` (description on stdin; give the title and what to check).
- Stop a task: `task set-status <id> on-hold`. Resume: set it back to `new`, `backlog` or `planned` according to where it stopped.
- Follow it: `task comments <id>`; every phase comments.
- Promote: merge `integration` into `main` yourself, then `task set-status <id> done`.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Task `on-hold` with "no sandbox worker could start" | the sandbox daemon is stopped | `sbx daemon status`, `sbx daemon start`, then put the task back |
| Run failed with "This worker already serves run" | a second sandbox run was started | the handler sends the task back and the dispatcher retries (written and checked on a recorded run, not yet seen live); if it repeats, look for a run started by hand |
| Task `integrated` with a comment "NOT deployed" | CI of `integration` red, or packaging, deployment or smoke test failed | `flow show <execution> --io`, fix, then `05_deploy.yml` with the commit |
| Plan comment `READY: no` | the planner needs a decision | answer in a comment, set the task back to `backlog` |
| Task never picked | blocked by an open `blockedBy` link, or held | `task links <id>`, `task show <id>` |
